# De un issue aprobado a un PR mergeado

## Why

Parte 3 de 3: después de `reunion-a-issues`. Un issue aprobado entra al flujo de seckert (FIX, SPEC o CHANGE) y termina en un PR que el usuario revisa y mergea (filtro 2).

## What

- Una skill `tomar <n>` lee el issue, crea su rama enlazada con `gh issue develop` (así GitHub lo muestra `in-progress`) y sigue la ruta sugerida; un CHANGE se escribe con `issue: #n` y sigue pidiendo tu «dale» antes del código.
- El PR lleva `Fixes #n` y el issue pasa a `in-review`; el merge lo cierra.
- Corre solo en local, en una sesión de Claude Code; la ejecución en la nube (GitHub Actions) queda fuera de esta parte.
